All `ccall` execution is synchronous but off the main thread, so no terminal UI freezes.
- Rewrote `html/app.js` — stripped all WASM imports (`QiWebModule`, `sqlite3InitModule`), replaced synchronous `ccall` calls with `worker.postMessage`. Added `isExecuting` input guard so keystrokes don't interleave with streaming output.
- Fixed double-quoting bug in `query-index-web.c` — 13 format strings had `'%s'` wrapping values already SQL-quoted by `sqlite3_mprintf("%q", ...)`, producing `''value''`. SQLite parsed `''` as empty-string literal, so every query was `symbol LIKE ''`, matching only the 24 rows whose symbol column was actually empty. Removed redundant `'...'` from all format strings.
- Rewrote `qi_sql_vsnprintf` (the custom `%q`/`%s`/`%d` shim) — the `sqlite3_mprintf` function calls `qi_sql_vsnprintf(NULL, 0, ...)` to measure output length before allocating, but the `while (*fmt && pos < size)` loop never ran when `size==0`, returning 0. Only 1 byte was allocated, and `%q` output (e.g. `'%'` — 3 chars) was fully truncated. The pattern vanished, producing `LIKE  ESCAPE` with no pattern → "near ESCAPE: syntax error". Added "measuring mode" (size==0 → count-only, no writes).
- Added comprehensive `console.log` debug tracing in both `qi-worker.js` and `app.js` to isolate the data-flow problem.

## Issues Encountered

### `sqlite3_mprintf` Shim Produced Empty Pattern for `%q`

- **Symptom:** `SQLITE_ERROR: sqlite3 result code 1: near "ESCAPE": syntax error` after removing double-quotes from format strings.
- **Root Cause:** The `qi_sql_vsnprintf` function called with `(NULL, 0)` for length measurement returned 0 instead of the actual needed length (3 for `'%'`). The 1-byte allocation truncated the entire `%q` output.
- **Fix:** Rewrote `qi_sql_vsnprintf` to support measuring mode — when `size==0`, all counting proceeds normally but no bytes are written to buffer. The function now returns the correct length.
- **Regression Risk:** `LOW`
- **Follow-Up:** `NONE`

### Double-Quoting of `%q`-Escaped Values in SQL Builder

- **Symptom:** Every query returned the same 24 results with empty SYM columns, regardless of the search pattern.
- **Root Cause:** `sqlite3_mprintf("%q", ...)` wraps values in `'...'`, but every SQL builder format string also had literal `'...'` around `%s` (e.g. `"(symbol LIKE '%s' ESCAPE '\\')"`). The result `''%''` was parsed by SQLite as `LIKE ''` (match empty strings) followed by noise.
- **Fix:** Removed redundant `'` from all 13 format strings: `'%s'` → `%s`.
- **Regression Risk:** `LOW`
- **Follow-Up:** `NONE`

## Residual Risks / Not Verified

- `@sqlite.org/sqlite-wasm` in a module worker — confirmed working in this session, but the package's internal WASM loading relies on `import.meta.url` resolution. If the package upgrades or its internal structure changes, `locateFile` may need to be passed explicitly.
- The `isExecuting` flag prevents all keystrokes during query execution. The window is typically <100ms, so it's not noticeable, but a long-running query would silently drop input. A proper input queue or non-blocking approach should replace this eventually.
- Debug `console.log` statements are still present in both `qi-worker.js` and `app.js` — should be removed or gated behind a debug flag before production.

## Notes / Design Decisions

- **Worker uses module import, not `importScripts()`:** Created via `new Worker('./qi-worker.js', {type: 'module'})`. The emcc flags `-sMODULARIZE=1 -sEXPORT_ES6=1` produce a `export default async function() {...}` module that worker `import` understands.
- **No `ENVIRONMENT` flag needed:** Emscripten's default `ENVIRONMENT` already includes `worker`, so the generated module works in both main-thread and worker contexts without special flags.
- **`isExecuting` gate vs. queuing:** Chose the simpler gate for now since query execution is synchronous and lightning-fast (<1ms for SQL build, <50ms for DB execute + format). A full command queue would be over-engineering at this stage.
- **Debug logging kept intentionally:** The `console.log` traces in both files were instrumental in isolating the `vsnprintf` / double-quoting bugs. Left in place for the next debugging session.

## Forward-Looking

1. **Verbose mode (`-v`):** The biggest visual improvement to output parity with the CLI. Requires column-schema awareness in the format function but no architectural changes.
2. **Strip debug logging:** Remove or gate all `console.log` statements behind a `DEBUG` flag before the next feature work session.
3. **Non-blocking input during query execution:** Replace `isExecuting` boolean gate with a proper input queue so long-running queries don't silently drop keystrokes. Low priority given current sub-100ms execution.
4. **`--and` / `--within` architectural decision:** Deferred from prior session. These require multi-statement SQL execution (temp tables), which the current single-SQL-string bridge cannot support.

1. **A one-page "SQL quoting in the qi-web bridge" reference** that explains: `%q` (from the custom shim) wraps in `'...'`, `sql_append` uses `%s` for insertion, and the resulting SQL string must not double-quote. Would have eliminated the 13-instance search-and-hopefully-not-miss-one fix cycle.

Would have made the `vsnprintf` bug immediately searchable.

## Freeform Thoughts

The two bugs at the center of this session were both in code written in the *previous* session — the `sqlite3_mprintf` shim and the SQL builder format strings. The shim had a silent truncation defect that only surfaced when the double-quoting was "fixed" (removing the redundant quotes exposed that the measurement pass was broken). The double-quoting itself was present from the start but masked by the fact that most queries hit the 24 empty-symbol rows and appeared to "work" with zero results or blank columns.

The worker migration was straightforward — about 20 minutes of coding — and the page load is noticeably faster because neither WASM module blocks the main thread during initialization. The worker message protocol (init/query → status/ready/output/error) is simple and explicit, making it easy to add new message types for features like `-v` formatting or context breakdowns.

The `isExecuting` boolean gate is crude but effective. In a terminal emulator where the user expects type-ahead, a proper input queue would be better, but the sub-100ms query execution makes it a non-issue for now. The real win is that the architecture now matches the research report's three-layer recommendation almost exactly: xterm.js owns the terminal surface, the worker owns query execution, and SQLite runs alongside qi in the worker (rather than in its own dedicated worker, which would add complexity for no benefit given the single-connection, in-memory DB).
