## Issues Encountered

### `index-c` aborts via `exit(1)` on oversized node extraction

- **Symptom:** `EXTRACTION ERROR ... binary_expression ... Text length: 1715 bytes ... Buffer size: 512` then process exit during indexing of `Parser.h`.
- **Root Cause:** C++ template misparse produced a giant `binary_expression`. A `field_expression` inside it hit the default branch of `extract_field_parent()`, which extracted the full left-side text into a 512-byte `SYMBOL_MAX_LENGTH` buffer; `safe_extract_node_text()` detected the overflow and called `exit(1)`.
- **Fix:** In `extract_field_parent()` (`c/c_language.c:1101`), check `ts_node_end_byte - ts_node_start_byte` against `buf_size` first; if too large, record an empty parent and return instead of aborting. A 1715-byte "parent symbol" is never useful.
- **Regression Risk:** `LOW` — only changes behavior on parents that exceed the buffer, which were previously fatal.
- **Follow-Up:** `NONE` (the broader C++-as-C misparse remains, but is now non-fatal).

### `index-c` segfaults (stack overflow) on deeply-nested expressions

- **Symptom:** `Segmentation fault (core dumped)` after the first fix; `coredumpctl` backtrace showed ~5800 stacked `visit_expression` frames.
- **Root Cause:** `visit_expression()` recurses through nested expressions with no depth limit. The misparsed C++ produced an expression tree thousands of nodes deep, exhausting the stack (~1.4 KB/frame on an 8 MB stack).
- **Fix:** Added `MAX_EXPRESSION_DEPTH` (1000) to `shared/constants.h` and a balanced static-counter depth guard in `visit_expression()` (`c/c_language.c`): early-return when depth is exceeded, `depth++` after the null check, single `depth--` at the lone exit point. Verified the function has no mid-body returns so the counter stays balanced.
- **Regression Risk:** `LOW` — real C nests far below 1000; limit is well under the ~5800 overflow point.
- **Follow-Up:** Other language indexers (`python_language.c`, `ts_language.c`) have their own `visit_expression`; not audited this session.

### `qi` queries extremely slow on the ~7.2 GB DB

- **Symptom:** Every `qi` query took a very long time.
- **Root Cause:** `idx_symbol` used BINARY collation; SQLite's LIKE→index optimization only fires for `COLLATE NOCASE` columns (or with `case_sensitive_like=ON`). qi matches case-insensitively, so every symbol query (and its companion width/count queries) was a full table scan.
- **Fix:** Changed `shared/database.c:109` to `CREATE INDEX ... ON code_index(symbol COLLATE NOCASE)`; supplied a one-time `DROP INDEX`/`CREATE INDEX` to fix the existing DB without a full re-index.
- **Regression Risk:** `LOW` — index semantics match the existing case-insensitive query behavior.
- **Follow-Up:** Leading-wildcard (`*contains*`) patterns still scan — would need FTS5/trigram. Tracked as a future idea.

## Notes / Design Decisions

- **C++-as-C is the shared root cause.** Both indexer crashes stem from parsing C++ headers with the C grammar. Fixes make the indexer *resilient* to misparse rather than attempting to parse C++ correctly — the right scope for `index-c`.
- **Width pre-pass kept, not refactored.** The precept review flagged the second `MAX(LENGTH(...))` query as a possible boundary leak, but `print_results_by_file` streams results (to serve unbounded output like `qi '*'`), so column widths genuinely cannot be known without a second pass. Per "comment the why" (#10), the intent was documented instead of removed. NOCASE makes the second pass cheap for normal queries.
- **Instrumentation favors one hook over many.** The plan recommends `sqlite3_trace_v2(SQLITE_TRACE_PROFILE)` as the backbone (Idea 2) over manual per-call-site stopwatches (Idea 1, skipped) — total coverage, zero call-site churn, information hidden at the DB boundary.

## Tooling Ideas

1. **A `qi --explain` / scan-detector mode** that runs `EXPLAIN QUERY PLAN` for each sub-query and flags any `SCAN code_index` — this would have surfaced the dead BINARY index immediately instead of via manual `sqlite3` planner inspection.
2. **A `make reindex-test` target** that builds and re-indexes a small adversarial corpus (a few misparse-prone C++ headers) under a leak/stack sanitizer, so crashes like these are caught in CI rather than on a 31k-file run.

## Documentation Ideas

1. **A "SQLite collation & the LIKE optimization" note** in `docs/PERFORMANCE.md` — explaining why indexed columns queried with case-insensitive `LIKE` must be `COLLATE NOCASE`, so this class of dead-index bug isn't reintroduced.
2. **An "indexing non-target languages" caveat** documenting that `index-c` on C++ (or any grammar mismatch) produces misparses and how the indexer defends against them (depth guard, bounded extraction) — sets expectations for users pointing `index-c` at mixed trees like LLVM.
