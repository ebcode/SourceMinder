- **Symptom:** User performs a swipe on iPhone; the `#scroll-log` div shows nothing
- **Root Cause:** Not yet confirmed. Hypothesis: fast swipes where `touchmove` fires zero times before `touchend` leave `touch.state === 'pressed'`; the old `pressed` branch returned without logging

- **Regression Risk:** LOW
- **Follow-Up:** If fast swipes consistently show `tap → focus`, the `pressed` branch needs velocity detection using the changedTouches final position vs `_touchWindow[0].y`

## Residual Risks / Not Verified

- Fast swipes on iPhone may still land as `pressed` (zero `touchmove` events before `touchend`) — now at least they'll log `tap → focus`, making the misclassification visible
- `_endGesture` takes no parameters, so if the `pressed` branch needs to detect movement it can't read `changedTouches[0].clientY` without a refactor to accept the event
- `touch.idle()` called from `idle` state (e.g., stray touchend with no preceding touchstart) would throw silently — the Proxy returns `undefined` and `undefined()` is a TypeError caught nowhere

---

## Notes / Design Decisions

- Used `Proxy` over explicit named-method objects or a `go(state)` function because it makes the invalid-transition guarantee structural: the method literally does not exist, rather than existing and checking
- `touch.swiping?.()` with optional chaining is the correct call pattern — `?.()` is a no-op when the method is absent, which is exactly the right behavior for "already swiping"
- `_endGesture` reads `touch.state` before calling `touch.idle()` so the `was` snapshot is clean regardless of what happens inside `idle()`
- Decision not to allow `idle → swiping` directly: would undermine the `pressed`/`post_stop` distinction that drives the tap-vs-swipe branch in `_endGesture`

## Freeform Thoughts

The `Proxy`-based state machine turned out to be an unusually clean fit for this problem. JavaScript's dynamic property lookup means "invalid transition = method doesn't exist" is a first-class language primitive, not a convention we have to enforce. The 9-line `statemachine.js` does real work.

The unresolved iPhone issue is likely a platform artifact: iOS throttles `touchmove` more aggressively than desktop browsers, and a fast tap-swipe may genuinely fire zero move events. If that's confirmed, the fix is a deliberate design choice rather than a bug — we just need to decide how much "implicit swipe" detection to build into the `pressed` exit path.
