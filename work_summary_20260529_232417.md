## Issues Encountered

### Empty columns rendered too wide in qi-web

- **Symptom:** `qi route --limit 100 -x noise -v -i func` in the browser showed `PAR`, `SCOPE`, `NS`, `MOD`, etc. padded to 8–10 chars even with no data; the CLI shrinks them to header width.
- **Root Cause:** `build_active_columns` (`qi-web-entry.c`) seeded `max_width` from a `WebColSpec.default_width` floor (8/10/20…). The first-pass data scan only ever *grows* that, so empty columns stayed at the wide floor.
- **Fix:** Seed `max_width` from the header width only; the data scan grows it to `max(header, data)`, matching the CLI. Removed the now-dead `default_width` field from the struct and all 10 registry rows.
- **Regression Risk:** LOW
- **Follow-Up:** Covered by the planned parity harness.

### qi-web printed a `Tip:` line the CLI doesn't

- **Symptom:** Browser output always ended with `Tip: Use -i <context> to narrow results`, even for a single un-truncated match; the CLI omits it there.
- **Root Cause:** `qi_web_format` emitted the Tip unconditionally in its footer. The CLI only prints it as part of the truncation breakdown (`get_context_summary`).
- **Fix:** Deleted the unconditional Tip from `qi_web_format`. `qi_web_format_breakdown` already emits it, and the worker only calls breakdown when `total > rows.length`.
- **Regression Risk:** LOW
- **Follow-Up:** NONE

### Browser served stale JS/WASM after `make web`

- **Symptom:** Had to open a private window to see the rebuilt code (the C-side fix compiles to `qi-web.wasm`).
- **Root Cause:** No cache-busting; the browser cached `qi-web.js`/`.wasm` and the hand-edited JS.
- **Fix:** Content-hashed build artifacts via manifest + `locateFile`, and per-load `?t` timestamps threaded through the dynamic-import chain. ES-module static specifiers can't carry a query string, so the volatile imports were converted to dynamic `import()` and the entry uses an inline bootstrap.
- **Regression Risk:** LOW — Node harness still loads the plain `qi-web.*` names (kept as copies); worker falls back to plain names if the manifest is absent.
- **Follow-Up:** NONE

## Notes / Design Decisions

- **Hybrid cache-busting:** content-hash the C-compiled artifacts (they change every rebuild, so a hash is as good as a timestamp and immutable-cacheable), but timestamp the hand-edited JS (busts on any edit without a build step). Manifest indirection is unavoidable because ES static import specifiers can't be interpolated.
- **Keep plain `qi-web.*` copies:** the Node harness (`load-qi.mjs`) loads them by plain name; keeping them also gives the worker a graceful fallback when no manifest exists.
- **Bust `qi-pipeline.js` too** (beyond the two files the user named): the worker statically imported it and it holds most shared query logic, so omitting it would reintroduce the staleness for the most important shared file. Flagged explicitly.
- **Parity: same DB file on both sides.** Running CLI (`--db-file <snapshot>`) and web against the identical `.browser.db` removes any "is it the same index?" doubt, so any diff is a real formatter/pipeline divergence.

## Freeform Thoughts

The two disparities fixed this session both came from the same structural pattern: the web formatter re-implements CLI behavior in a parallel registry/format function, and small seeded defaults (a width floor, an always-on Tip) drift from the CLI's computed/conditional logic. That's a strong argument for the parity harness paying for itself quickly — there are almost certainly more of these latent in the column/mode formatting, and an automated CLI-vs-web diff is the cheapest way to keep the twins honest. Using `qi` to read the C this session worked well for symbol lookup and `-e --raw` definition reading; the main friction was JS imports and filename-string searches, where it isn't the right tool.
