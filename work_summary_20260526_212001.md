## Issues Encountered

### `sqlite3_mprintf` Shim Produced `(null)` for `%q`

- **Symptom:** SQL contained `symbol LIKE '(null)'`, returning zero results.
- **Root Cause:** The shim passed `%q` (SQLite-specific format) to `vsnprintf`, which doesn't understand it and outputs `(null)`.
- **Fix:** Wrote a custom `qi_sql_vsnprintf` that handles `%q` (wraps strings in single quotes, doubles embedded quotes, handles NULL → `NULL`), plus `%s` and `%d`.
- **Regression Risk:** `LOW`
- **Follow-Up:** None — the shim is functionally correct for all format patterns used in the codebase.

### Shared Modules Pulled in Tree-Sitter Dependencies

- **Symptom:** Emcc compilation of `shared/string_utils.c` and `shared/database.c` failed because `<tree_sitter/api.h>` was not available.
- **Root Cause:** `shared/string_utils.h` includes `<tree_sitter/api.h>` for `TSNode` types used by `safe_extract_node_text` and `format_source_location` — functions the web module never calls.
- **Fix:** Created `wasm/tree_sitter/api.h` stub with inline no-op implementations of all tree-sitter functions, plus `wasm/execinfo.h` stub for `backtrace()`.
- **Regression Risk:** `LOW`
- **Follow-Up:** If tree-sitter's API surface changes, the stub may need updating.

### xterm.js v5.3.0 Not ES Module Compatible

- **Symptom:** `SyntaxError: doesn't provide an export named 'Terminal'` and `'default'`.
- **Root Cause:** xterm v5.3.0 is a UMD bundle (`!function(e,t){...}`), not an ES module. The `@xterm/addon-fit` package has the same issue, plus it double-wraps the export: `window.FitAddon` is `{FitAddon: class}`, not the class directly.
- **Fix:** Loaded both as regular `<script>` tags in HTML, accessed `window.Terminal` directly, and extracted `FitAddon.FitAddon` as `FitAddonCtor`.
- **Regression Risk:** `LOW`
- **Follow-Up:** Upgrade to `@xterm/xterm` (the current package) which has proper ESM support.

### Configure-Generated Makefile Lost Between Sessions

- **Symptom:** `make web` and `make web-smoke` targets were absent after regeneration.
- **Root Cause:** The Makefile is gitignored and regenerated by `./configure`. Previous session's targets were added directly to the Makefile, not to the configure template.
- **Fix:** Added `WEB_SRC`, `WEB_ENTRY_SRC`, `WEB_SHARED_SRC`, `WASM_DIR` variables and both `web`/`web-smoke` targets into the configure script's heredoc template so they persist across regenerations.
- **Regression Risk:** `LOW`

## Residual Risks / Not Verified

- xterm.js v5.3.0 is deprecated; the current version is `@xterm/xterm`. The UMD→ESM workaround is fragile.
- The `sqlite3_mprintf` shim handles `%q`, `%s`, and `%d` but not other SQLite format specifiers (`%Q`, `%w`, `%z`). The codebase currently only uses `%q`, `%s`, and `%d`.
- `--and` and `--within` flags require multi-statement SQL execution (temp tables), which the current single-SQL-string bridge cannot support. Deferred to future architectural decision (WASIX or multi-statement bridge).
- No automated regression tests for the WASM module itself — testing is manual (browser console + visual inspection).

## Notes / Design Decisions

- **No sqlite3 in WASM:** The C/WASM module builds SQL and formats output; JS owns the DB connection via `@sqlite.org/sqlite-wasm`. This avoids dual sqlite3 runtimes and keeps the WASM module small (34K).
- **Embedded patterns instead of bind params:** Changed `build_query_filters_web` OR mode from `(symbol LIKE ?)` to `(symbol LIKE '<embedded>')`. This eliminates bind-parameter marshaling across the JS↔WASM boundary, simplifying the bridge API to a single SQL string.
- **Two-pass formatting:** The format function scans TSV rows twice — once for column width calculation, once for output. This keeps the format function stateless and avoids storing all rows in WASM memory.
- **Tree-sitter stub approach:** Rather than splitting shared modules into tree-sitter-dependent and tree-sitter-independent halves, a minimal stub header allows compiling the exact same shared source files for both native and WASM targets.

## Forward-Looking

1. **Verbose mode (`-v`) and `--columns`** — the biggest visual improvement to output parity with the CLI. Requires column-schema awareness in the format function but no architectural changes.
2. **Context breakdown in output** — add `Result breakdown:` line after matches, mirroring the CLI. Requires a JS-side GROUP BY query and a small format function extension.
3. **Investigate WASIX for `--and`/`--within`** — WASIX provides TTY and full POSIX support in WASM. Compiling the native `qi` binary for `wasm32-wasix` could eliminate the custom bridge entirely and give us temp tables, definition lookups, and source-file access in one step.
4. **Source-fetch host bridge** — for `-e`, `-C`, `-A`, `-B`, and `--toc`. The C code would identify needed file ranges and JS would `fetch()` them from a static file server, passing content back for rendering.
5. **Upgrade to `@xterm/xterm`** — the current xterm (`xterm@5.3.0`) is deprecated and uses UMD. The new `@xterm/xterm` has proper ESM support, eliminating the fragile script-tag workaround.

## Freeform Thoughts

The hardest part of this session wasn't the C code or the algorithm logic — those were straightforward extractions from the well-factored `query-index.c`. The real friction was at the boundaries: getting emcc to compile shared modules with tree-sitter contamination, finding the right emscripten flags for ES6 module output, diagnosing CJS/UMD module format mismatches with xterm.js, and handling the `%q` format specifier that `vsnprintf` silently corrupts. Each of these was a 5-minute fix once identified but a 20-minute search to isolate.

The bridge architecture (C builds SQL, JS executes, C formats) worked surprisingly well on the first try once the `%q` shim was fixed. The two-pass TSV format approach is clean and keeps the WASM module stateless. The 34K `.wasm` binary is small enough to feel like a library rather than a runtime.

The next big decision point is whether to stay on this bridge architecture for the long term or pivot to WASIX. WASIX would let us compile the full native `qi` binary for the browser with TTY, threads, fork, and filesystem support, eliminating the custom bridge entirely. But it's a heavier dependency and less proven. The bridge approach keeps us in control but requires us to reimplement more of the CLI's execution model (temp tables for `--and`, definition lookups for `--within`) in either C or JS.
