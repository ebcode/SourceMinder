## Issues Encountered

### Short-Pattern Auto-Retry Produced 995 Lines

- **Symptom:** `qi a` in the browser returned hundreds of results instead of a "too short" note.
- **Root Cause:** `qi_web_format_no_results` checked `wild > 0` (partial matches exist) before attempting retry, but did not check pattern length. For `a`, `NR_WILD` SQL matched many things via `*a*`, so `wild > 0` → retry fired.
- **Fix:** Added `strlen(pat[i]) < 2` branch before the `wild > 0` retry check; emits the Note and skips retry.
- **Regression Risk:** LOW — only affects patterns shorter than 2 characters; all other paths unchanged.
- **Follow-Up:** NONE

### Sourceminder In-Place DB Was Empty After Re-Index

- **Symptom:** Parity tests failed with `native 0 / web N lines` — native qi returned zero results for every case.
- **Root Cause:** The re-index created a fresh 56K empty `code-index.db` in `html/sources/sourceminder/` (the index ran there and found no source files to index). The parity harness was reading that empty DB for native queries.
- **Fix:** Copied the full 19M main `code-index.db` to the sourceminder source tree, regenerated the browser snapshot, and corrected the `projects.json` `dbUrl` entry which still pointed to the old `./code-index.browser.db`.
- **Regression Risk:** NONE
- **Follow-Up:** `refresh-sourceminder.sh` makes the correct post-reindex workflow explicit and repeatable.

### `row_count` Out of Scope at Footer

- **Symptom:** Compiler error (C) would have occurred at the `if (total > row_count)` footer after hoisting `row_count` to count only displayed rows — the variable was declared inside the second-pass block.
- **Root Cause:** The second-pass is wrapped in `{ char *rows_copy = ... }` for scope management; the original `int row_count = 0` was inside that block.
- **Fix:** Declared `row_count` immediately before the block opens (with a comment) and removed the inner declaration.
- **Regression Risk:** LOW — behavior identical for cases without per-file filtering.
- **Follow-Up:** NONE

### Initial `--limit-per-file` Parity Case Showed 1 Row vs 5

- **Symptom:** `qi % -i func --limit-per-file 1 --limit 5` — native showed 5 rows (1 from each of 5 files), web showed 1 row.
- **Root Cause:** The browser snapshot returns the first 5 SQL rows all from `./qi-web-entry.c` (which has 36 functions). With `limit_per_file=1`, the C formatter correctly shows 1 row. Native fetches ALL 944 rows with no SQL LIMIT, then walks them showing 1 per file until 5 total — a fundamental SQL-vs-display-limit architectural difference.
- **Fix:** Changed the parity case to `qi COLUMN -i func --limit-per-file 2 --limit 5`, where the first 5 SQL rows naturally span 3 files (2 from qi-web-entry.c, 1 from query-index-web.c, 2 from query-index.c), so both sides show identical output.
- **Regression Risk:** NONE — test case selection only.
- **Follow-Up:** The underlying architectural difference (web SQL LIMIT = display limit; native SQL has no limit) is a known pre-existing constraint documented in `WEB_QI_FLAGS_PLAN.md`.

## Residual Risks / Not Verified

- **`--full` flag** — identified as a gap, confirmed with parity tool, not implemented. Requires expanding all column headers (`SYMBOL`/`CONTEXT`) and context values (`FUNCTION`) via `display_context` twin. Lower priority than `--limit-per-file`.
- **`--limit-per-file` cross-file SQL interaction** — when the SQL LIMIT rows come entirely from one file, per-file filtering produces fewer displayed rows than native (which has no SQL LIMIT). This is the pre-existing architectural trade-off. The parity test case was chosen to avoid this edge.
- **`refresh-sourceminder.sh` assumes repo root as cwd** — no guard for running from the wrong directory (besides the `code-index.db` existence check). If run from `html/sources/`, it fails to find source files.
- **Browser-snapshot version key** — `projects.json` has `"version": "1"` for sourceminder; the Cache-Storage refresh rule requires bumping `version` for browsers that cached the old snapshot. Not bumped this session.

## Notes / Design Decisions

- **TOC-first parity analysis**: `qi % -f <file> --toc` across `query-index.c`, `query-index-web.c`, and `qi-web-entry.c` gave a structural diff of 77 vs 9+36 functions without reading any implementation code. Two of three functions with no obvious web twin turned out to be either already-dead code (`unescape_pattern` — commented-out block) or display-only (`display_context` — the mechanism `--full` uses). The TOC approach found both real gaps in under 10 minutes.
- **`row_count` vs `shown` in footer**: the change from `if (total > shown)` to `if (total > row_count)` is load-bearing for `--limit-per-file` — when per-file filtering reduces displayed rows below the SQL fetch count, the old condition would have underreported. For cases without per-file filtering, `row_count == shown` always, so existing parity cases are unaffected.
- **`refresh-sourceminder.sh` skips missing files**: transient build artifacts (hashed `qi-web.*.js` etc.) are in the index but not on disk after `make clean` or `make web`. The script checks existence before copying rather than failing on the first missing file.
- **Parity case selection for `--limit-per-file`**: the chosen case (`COLUMN -i func --limit-per-file 2 --limit 5`) verifies both that the flag is parsed AND that the formatter produces the correct grouped output across 3 files. The limit IS hit (5 displayed = 5 limit), so native calls `get_total_count` — same path the web uses via COUNT_SQL — making the footer identical.

## Freeform Thoughts

The TOC approach for parity gap discovery was more productive than expected. Two qi commands (`qi % -f query-index.c --toc` and `qi % -f qi-web-entry.c --toc`) gave a clean structural diff and surfaced both remaining unimplemented flags without touching any implementation code. The only false positive (`unescape_pattern`) resolved in one `qi unescape_pattern -e --raw` call that showed the function was inside a commented-out block. Total research time: under 15 minutes for two confirmed parity gaps.

The `--limit-per-file` SQL-vs-display-limit issue is worth keeping in mind for future flags. The web's SQL LIMIT equals the display limit, which works perfectly when filtering is absent — but any C-side display filter (per-file limit, future column value deduplication, etc.) that reduces the displayed count below the SQL fetch will hit this ceiling. The parity test case selection discipline (choose a case where the SQL fetch spans enough files that filtering doesn't reduce the displayed count below the limit) is reusable for any future display-side filter.

The sourceminder db recovery was a good reminder: `make` (re-index from root) touches `code-index.db` at the root but also creates empty DBs wherever the indexer is invoked with a new path. The `refresh-sourceminder.sh` script closes this loop for the primary demo project. Any additional projects in `html/sources/` would need the same treatment after a re-index.
