## Issues Encountered

### `WAL-mode Browser Snapshot`

- **Symptom:** `The browser page initialized SQLite WASM but failed when querying the imported database.`
- **Root Cause:** `The snapshot database imported into the browser was still in WAL mode, which is not safe for the browser deserialize/import path without the WAL sidecar state.`
- **Fix:** `Created html/code-index.browser.db from the live repository DB and converted it to non-WAL mode with PRAGMA journal_mode=DELETE; VACUUM;.`
- **Regression Risk:** `LOW`
- **Follow-Up:** `Refresh the browser snapshot with the documented two-step backup and non-WAL conversion whenever the repo index changes materially.`

### `Initial Browser DB Library Choice`

- **Symptom:** `The first working browser prototype used sql.js, which did not match the intended upstream SQLite WASM path for future qi integration.`
- **Root Cause:** `Emscripten was not initially available, so the shortest route to a working browser-side DB was sql.js.`
- **Fix:** `After Emscripten became available, replaced the harness with SQLite's official browser WASM package and switched loading to sqlite3_deserialize() plus the oo1 API.`
- **Regression Risk:** `LOW`
- **Follow-Up:** `Keep building against the official SQLite WASM surface so later qi/WASM work does not depend on a divergent browser DB runtime.`

- `Chose a browser-safe snapshot database in html/ rather than reading the live repo WAL database directly, because browser-side import should not depend on WAL sidecar state.`
