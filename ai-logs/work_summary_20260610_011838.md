## Notes / Design Decisions

- **Minimal scope for Python nested defs:** A `def` inside a `def` gets empty parent (not the enclosing function). The ancestor walk stops only at `class_definition`. This is the pragmatic choice from the plan — syntactic-parent purity would also populate nested defs, but that was deferred.
- **C ARG parent is pragmatic, not grammatical:** The parent of a parameter is the function name, not a class or type. This is explicitly a code-exploration convenience (consistent with how PHP and TypeScript already index ARG rows) rather than a claim about the grammar hierarchy.
- **PHP ancestor walk preferred over Rust tracker for TS/Python:** The ancestor walk is stateless and nesting-safe. The Rust `g_current_impl` pattern was only used for Perl because `package` is a statement, not a block — there is no ancestor to walk to.

## Documentation Ideas

1. **`docs/PARENT_SYMBOL_CONVENTION.md`** — a concise reference describing what `parent_symbol` means for each context type (FUNC = enclosing class/interface/impl; ARG = enclosing function; PROP = enclosing class/interface; CLASS = superclass in Python). The convention is implicit across four language files right now; a single doc would prevent future implementers from choosing the wrong semantic.
2. **`docs/INDEXER_PATTERNS.md`** — a catalogue of the two established patterns for conveying enclosing context (ancestor walk vs. file-scope tracker), with the rule for when to use each and a pointer to the canonical implementation of each. Currently this knowledge lives only in `FIX_PAR_NS.md` and in the PHP/Rust source.

## Freeform Thoughts

The plan in `FIX_PAR_NS.md` was unusually complete — having the canonical PHP and Rust implementations called out by line number made the session fast. The only real surprise was the `symbol` scoping issue in the C file: the original code had the function name and the parameter list extraction in sibling `if` blocks with no reason to share state, so the hoisting was a necessary mechanical fix rather than a design change.

The C ARG change is notably different in character from the TS/Python/Perl changes: those were fixing a gap where data existed in the grammar but wasn't being captured. The C ARG parent is purely additive metadata with no direct grammar analog — the function name is already known at call time, it just wasn't threaded through. The pragmatic framing from the user is the right one.
