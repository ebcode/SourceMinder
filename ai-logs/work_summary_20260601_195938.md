## Issues Encountered

### `ts_language_symbol_for_name` third argument — not a bug

- **Symptom:** `ack 16` flagged the `16` in four `ts_language_symbol_for_name(language, "...", 16, true)` calls as suspicious hardcoded values.
- **Root Cause:** These are `strlen()` of the string literal being passed — an intrinsic property of the symbol name, not a configurable constant.
- **Fix:** No change made; confirmed correct by checking C, Go, and other language implementations which follow the same pattern.
- **Regression Risk:** NONE
- **Follow-Up:** NONE

### `SOURCE_LOCATION_MAX_LENGTH` constant value stale

- **Symptom:** `SOURCE_LOCATION_MAX_LENGTH` defined at 32 in `constants.h`, but all language files used `location[128]` and never referenced the constant.
- **Root Cause:** The constant was defined for the `database.h` struct field and never propagated to local buffer declarations.
- **Fix:** Bumped constant to 128, replaced all local buffer declarations codebase-wide.
- **Regression Risk:** LOW — `database.h` struct field `source_location[SOURCE_LOCATION_MAX_LENGTH]` grows from 32 to 128 bytes; this may slightly increase `ParseEntry` struct size, but is strictly safer.
- **Follow-Up:** Verify struct layout impact is acceptable (see Residual Risks).

## Notes / Design Decisions

- `ts_language_symbol_for_name` string-length arguments are intentionally kept as inline integer literals matching `strlen()` of the adjacent string. Using `sizeof("...") - 1` would be equivalent but the current style is consistent and readable.
- `candidates[256]` (a local `TSNode` array in `perl_language.c:429`) was identified as another hardcoded number but left alone — it has no corresponding constant in `constants.h` and is a purely local algorithmic limit, not a shared configuration value.

## Tooling Ideas

1. **`qi --literal-numbers` filter** — a mode that surfaces indexed string/comment tokens matching bare integer patterns, scoped to a file. Would have made the initial triage ("which 16s are strlen, which are buffer sizes?") much faster than cross-referencing `ack` output manually.
2. **Cross-file constant coverage checker** — a small script that greps for numeric literals in `*.c` files, filters out loop variables and return codes, and flags any that match values defined in `constants.h` but aren't referencing the constant by name. Would have found all four issues in one pass instead of iteratively.

## Documentation Ideas

1. **`constants.h` usage guide** — a short doc (or inline comment block at the top of `constants.h`) mapping each constant to which file types and contexts are expected to use it. Would have made it obvious that `SOURCE_LOCATION_MAX_LENGTH` belongs in local `location[]` buffers, not just the database struct.
2. **`ts_language_symbol_for_name` convention note** — a comment in `shared/` or the language-implementation guide explaining that the third argument is always `strlen()` of the string literal and should never be replaced with a named constant. Saves future readers from investigating it as a bug.

## Freeform Thoughts

The `ack 16` starting point was a good instinct — collateral literal audits like this often surface more than the original target. The `location[128]` issue was a better catch than the original `fn_text[16]` bug, since it touched every language file and had a stale constant behind it. The fact that `SOURCE_LOCATION_MAX_LENGTH` existed but wasn't used in the local buffers is a classic "defined for one consumer, forgotten by everyone else" pattern — worth keeping an eye on in the other constants too.
