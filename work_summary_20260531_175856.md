## Context Established

- The starting point was a plan item from the prior session: "Add a composite index — `(directory, filename, symbol, line)` would speed up EXISTS subqueries significantly." Used `sqlite3` directly against `code-index.db` and `EXPLAIN QUERY PLAN` to test the claim before writing any code.
- Confirmed the `--and` proximity check query (`SELECT 1 FROM code_index WHERE filename = ? AND directory = ? AND line BETWEEN ? AND ? AND symbol LIKE ? LIMIT 1`) was doing a full per-file scan via `idx_file_location`, scanning up to 8,309 rows for `query-index.c` on every secondary-pattern check.
- Discovered that for this query, `(directory, filename, line)` beats `(directory, filename, symbol, line)`: SQLite's LIKE optimization can only use one range column per index, and it correctly prefers the tighter `line BETWEEN` bound over a symbol prefix range.
- Audited all 13 existing indexes with `EXPLAIN QUERY PLAN` across common query patterns and found: (1) three indexes were structurally redundant, (2) every text-column index except `idx_symbol` was BINARY-collated, making them invisible to LIKE queries — the standard filter flags (`-f`, `-p`, `-m`, `-s`, `-ns`, `-t`, `-c`) were all doing full table scans.

## Work Completed

- Added `idx_file_line ON code_index(directory, filename, line)` — confirmed by EXPLAIN as the chosen plan for the `--and` proximity check (narrows from ~8k rows to the ~50-row line window).
- Dropped `idx_file_location (directory, filename)` — fully subsumed by `idx_file_line`; EXPLAIN confirmed SQLite never chose it once `idx_file_line` existed.
- Dropped `idx_directory (directory)` — no code path in `build_common_filters` generates a directory-only WHERE clause; always paired with filename.
- Dropped `idx_parent_symbol (parent_symbol)` — subsumed by `idx_parent_context (parent_symbol, context)` whose leftmost column covers single-column parent lookups.
- Fixed NOCASE collation on all text-column indexes: `idx_filename`, `idx_parent_context` (on `parent_symbol`), and all X-Macro-generated column indexes (`idx_scope`, `idx_modifier`, `idx_namespace`, `idx_clue`, `idx_type`). EXPLAIN confirmed each now uses its index for prefix LIKE patterns.
- Added drop-before-recreate logic in `db_init` so existing databases pick up collation changes automatically: explicit `DROP INDEX IF EXISTS` for `idx_filename` and `idx_parent_context`, plus an X-Macro DROP pass for all column indexes, before the CREATE pass.

## Issues Encountered

### DROP statements in `db_init` did not fire on incremental reindex

- **Symptom:** After first make + reindex (without deleting the old DB), the three redundant indexes were still present in `code-index.db`.
- **Root Cause:** The DROPs were confirmed present in the compiled binary via `strings`. Most likely cause: the indexer was run against the old binary or the DB was locked. Running the same DROP statements manually via `sqlite3` succeeded immediately.
- **Fix:** Deleted `code-index.db` and reindexed from scratch. All indexes correct on a fresh DB.
- **Regression Risk:** `LOW` — the DROP statements in `db_init` are correct and idempotent; the workaround of deleting the DB before a schema-change reindex is standard practice anyway.
- **Follow-Up:** The root cause of why `db_init`'s DROPs didn't fire on the existing DB is unconfirmed. Worth investigating whether the indexer opens the DB in a mode that silently skips DDL, or whether a WAL/locking condition prevented the drops.

## Residual Risks / Not Verified

- The `--and` proximity check performance improvement has not been benchmarked on the large llvm-project database (~7.2 GB, 31k files). The EXPLAIN improvement is confirmed; the real-world speedup on large files is assumed but unmeasured.
- The drop-before-recreate logic in `db_init` runs on every database open (read or write). For read-only opens (e.g., `qi` queries), the DROPs may fail silently if the DB is read-only or locked. This is harmless but worth understanding.
- `idx_file_line` uses BINARY collation on `directory` and `filename`. For `-f shared/` style patterns, the main query path uses `idx_symbol` anyway (confirmed by EXPLAIN), but if that changes the file-location index won't assist LIKE lookups.
- Other language indexers (`python_language.c`, `ts_language.c`, etc.) were not audited for recursion depth or parent-extraction overflow issues similar to those fixed in the prior session for `c_language.c`.

## Notes / Design Decisions

- Chose `(directory, filename, line)` over the originally proposed `(directory, filename, symbol, line)`: EXPLAIN confirmed SQLite always prefers the line-bounded version because LIKE is itself a range and only one range column benefits per composite index.
- The drop-before-recreate pattern in `db_init` was chosen over alternatives (e.g., schema versioning, migration table) to keep complexity minimal. Idempotent `IF EXISTS` drops are harmless on fresh DBs and automatic on existing ones.
- `idx_parent_symbol` is still created by the X-Macro (since `parent_symbol` is in `column_schema.def`) and immediately dropped at the end of the schema string. A future cleanup could introduce a `COLUMN_COMPOSITE` macro variant to skip X-Macro index generation for columns already covered by a composite index — but with 30+ expansion sites, the change was deferred.

## Freeform Thoughts

The BINARY-vs-NOCASE collation issue was a sleeper bug: the indexes existed, the queries ran, but the indexes were silently unused for every LIKE query. The only symptom was query slowness — no errors, no warnings. It's the kind of thing that only surfaces when you run EXPLAIN QUERY PLAN, which most users never do. The prior session fixed `idx_symbol` (the most critical one) after noticing slowness on a 7.2 GB DB; this session caught all the others by doing a systematic audit rather than waiting for each one to hurt.

The `qi` tool was the right instrument for the code investigation but `sqlite3` was indispensable for schema and query-plan work. A tight integration between the two (e.g., `qi --explain`) would close that gap.
