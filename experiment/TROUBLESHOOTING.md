# Troubleshooting — Common Failure Modes

A cheat-sheet of failure modes encountered during experiment development.
Each entry describes the symptom, the root cause, and the fix.

## Run-time Failures

### `ValueError` on LimitsExceeded — "invalid literal for int()"

**Symptom:** A run exits with `exit_status: "ValueError"` and the error log
shows `invalid literal for int(): '\x1b[6~...'` or similar terminal escape
sequences.

**Root cause:** mini-swe-agent's `InteractiveAgent` checks `sys.stdin.isatty()`.
When stdin is a TTY (normal terminal launch), hitting the turn limit prompts
`int(input("New step limit:"))`, which consumes the next buffered line of
terminal input and fails to parse it as an integer.

**Fix:** The orchestrator (`run_experiment.py` → `run_pilot.py`) already passes
`stdin=subprocess.DEVNULL`, which makes `isatty()` return `False` and cleanly
re-raises `LimitsExceeded`. If launching `run_pilot.py` directly from a
terminal, you risk this hang. Pass `--quiet` to `run_experiment.py`.

**Re-run contaminated runs:** `run_experiment.py --retry-failed` re-runs
crashed runs (those with a non-clean `exit_status` — anything not `Submitted`
or `LimitsExceeded`).

### Run produces no output — is it hanging?

**Symptom:** A run starts, Docker pulls the image, then the terminal goes
silent for minutes with no progress indicators.

**Root cause:** Likely *not* a hang — the API is slow and the model is thinking.
Mini-swe-agent waits for `litellm.completion()` which can take 30–120 seconds
per turn depending on load.

**Fix:** Use `--quiet` mode. `run_experiment.py --quiet` prints the log path
before starting, then you can `tail -f experiment/logs/<arm>/<instance>/<rep>.log`
to see live per-turn output (commands, API responses, costs). If the log file
stops growing for >2 minutes, the run has likely stalled.

### Network stall — run hangs mid-request

**Symptom:** No new log output for >5 minutes, no error message, `docker ps`
shows the container still running.

**Root cause:** `litellm.completion()` can stall on network errors without
raising an exception (retry only fires on explicit exceptions, not silent
timeouts). This is distinct from the `input()` hang above.

**Fix:** Add `model_kwargs.timeout` to `config/shared.yaml` (not yet
implemented in the config). For now, kill the run (`kill <pid>`) and the
orchestrator will re-run it on restart if incomplete. Check `run_ledger.jsonl`
for the attempt record.

### Stale Docker containers from crashed runs

**Symptom:** `docker ps` shows containers named `minisweagent-*` that have been
running for longer than the per-instance timeout, with no parent process.

**Root cause:** mini-swe-agent doesn't always clean up Docker containers when
the parent process is killed mid-run (SIGTERM/SIGKILL). The `run_args` includes
`--rm` so clean exits auto-remove, but if the container's init process outlives
the Python process, Docker waits.

**Fix:** Manual cleanup:
```bash
docker rm -f $(docker ps -q --filter name=minisweagent)
```

**Prevention:** Run this between batches:
```bash
docker ps --filter name=mini --format 'table {{.ID}}\t{{.RunningFor}}\t{{.Names}}'
```

## Configuration Errors

### `DEEPSEEK_API_KEY` not set

**Symptom:** `run_experiment.py` exits with "DEEPSEEK_API_KEY is not set and
API_KEY is empty".

**Fix:** Either:
```bash
export DEEPSEEK_API_KEY="sk-..."
```
Or paste your key into the `API_KEY` constant at the top of `run_experiment.py`:
```python
API_KEY = "sk-..."
```
The inline constant takes precedence over the environment variable.

### `KeyError: instance not found`

**Symptom:** `run_pilot.py` fails with a `KeyError` when loading the instance.

**Root cause:** The `--subset` flag doesn't match the instance's dataset.
`--subset verified` loads from `princeton-nlp/SWE-bench_Verified`; `--subset lite`
loads from `princeton-nlp/SWE-bench_Lite`. An instance ID valid in one subset
may not exist in the other.

**Fix:** Verify the instance belongs to your subset. All 20 instances in
`verified_instance_ids.txt` are from the Verified set; use `--subset verified`
(which is the default).

### "attempt to write a readonly database"

**Symptom:** The agent runs `qi` queries but gets SQLite errors about a
read-only database.

**Root cause:** The DB was mounted with `:ro` (read-only), but SQLite needs a
writable WAL/lock file even for read-only queries.

**Fix:** The current config mounts the DB read-write (no `:ro`) because the
container is ephemeral (`--rm`). If you see this error, check the
per-instance config generated by `run_pilot.py`'s `make_treatment_config()`
and ensure the DB mount lacks `:ro`.

### Config duplication — wrong setting doesn't take effect

**Symptom:** You changed `step_limit` or `model_name` but runs still use the
old value.

**Root cause:** Before `shared.yaml` was introduced, these settings were
duplicated in `control.yaml` and `treatment.yaml`. If you're editing an older
checkout or the arm-specific files by mistake, your changes may be overridden
or only apply to one arm.

**Fix:** Edit `experiment/config/shared.yaml` for settings shared across both
arms (step_limit, model_name, cost_limit, timeout). Arm-specific files
(`control.yaml`, `treatment.yaml`) contain only arm-specific differences
(instance_template, run_args).

## Docker / Pre-index Issues

### Docker image not found locally

**Symptom:** `pre_index.py` or `run_pilot.py` fails with "image not found".

**Fix:** Pull the image first:
```bash
docker pull swebench/sweb.eval.x86_64.<repo>_1776_<id>:latest
```
Or use `pre_index.py --pull` to pull all images before indexing.

### `env_startup_command` doesn't copy qi into the container

**Symptom:** qi is not found inside the container despite being specified in
the config.

**Root cause:** `env_startup_command` is broken in mini-swe-agent v2.4.1 with
`DockerEnvironment`. Files specified there are not copied at container startup.

**Fix:** The experiment uses direct Docker volume mounts (`-v`) in `run_args`
instead. The qi binary and code-index.db are mounted into the container at
`/usr/local/bin/qi` and `/testbed/code-index.db` respectively. This is handled
automatically by `run_pilot.py`'s `make_treatment_config()`.

## Analysis Issues

### Stray trajectories from other instances inflating analysis

**Symptom:** The analyzer reports more runs than expected (e.g., 22 runs for a
10/arm instance).

**Root cause:** Trajectories from concurrent or different-instance runs have
been written to the same `logs/` tree. The analyzer globs `**/*.traj.json` and
doesn't filter by instance.

**Fix:** Either (a) scope the analyzer to a subset of the log tree, or (b)
move unwanted trajectories out of the scanned tree before running analysis.

### Predictions dedup — only 1 run evaluated per instance

**Symptom:** Despite running 10 reps per arm, the harness evaluation produces
only 1 result per instance.

**Root cause:** SWE-bench's harness deduplicates predictions by `instance_id`
only — putting all runs in one prediction file keeps only the last prediction
per instance.

**Fix:** `evaluate_patches.py` handles this automatically by batching per
`(arm, rep)` group, where instance_ids are unique. You should never see this
issue when using the provided scripts.

## Quick Health Checks

```bash
# Check which runs have trajectories
find experiment/logs -name '*.traj.json' | wc -l

# Check manifest states (completed/failed/started)
find experiment/logs -name '*.manifest.json' -exec sh -c 'jq -r ".status" "$1"' _ {} \; | sort | uniq -c

# Check Docker containers
docker ps --filter name=mini --format '{{.Names}} {{.RunningFor}}'

# Check a specific run's progress
tail -f experiment/logs/control/django__django-10554/1.log

# Check the ledger for recent failures
tail -20 experiment/logs/run_ledger.jsonl | jq .
```
