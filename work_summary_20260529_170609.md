## Issues Encountered

### WAL-mode browser snapshot → `SQLITE_CANTOPEN` (caught by the harness on its first real run)

- **Symptom:** After the user regenerated `code-index.browser.db`, all 7 integration cases threw `SQLITE_CANTOPEN` at query time.
- **Root Cause:** The regenerated snapshot was in WAL journal mode; `sqlite3_deserialize` cannot open the absent `-wal` sidecar. This is the identical deserialize path the browser worker uses — so the live app would have been broken with that DB too.
- **Fix:** Folded the snapshot with `PRAGMA journal_mode=DELETE; VACUUM;`; codified `VACUUM INTO` into `browser-snapshot.sh` so the fold is unskippable.
- **Regression Risk:** NONE
- **Follow-Up:** NONE — documented as an invariant in `html/sources/README.md`.

### Regular query mode applied `LIMIT 0` literally (Medium review finding)

- **Symptom:** The main path did `sql + ' LIMIT ' + limit` unconditionally; a `LIMIT|0` ("no limit") would return zero displayed rows while `total` stayed positive. TOC/files modes already guarded with `limit > 0`.
- **Root Cause:** Inconsistent limit handling across modes.
- **Fix:** `var mainQuery = limit > 0 ? (sql + ' LIMIT ' + limit) : sql;`
- **Regression Risk:** NONE — and currently latent: `qi_web_build` rejects `--limit <= 0` ("must be positive"), so no build path emits `LIMIT|0` today. Defense-in-depth/consistency.
- **Follow-Up:** Open design question (out of scope): whether `--limit 0` should mean "unlimited" in the web parser.

### `injectWhereClause` used raw `indexOf` (Medium review finding)

- **Symptom:** Injected the `--within` clause before the first `GROUP BY`/`ORDER BY`/`LIMIT` *anywhere* in the SQL — could land inside a subquery or a string literal.
- **Root Cause:** Substring scan ignored paren depth and string-literal state.
- **Fix:** `findOuterTailClause()` walks the SQL tracking paren depth and `''`-aware quote state, matching keywords only at depth 0 outside literals. Added 8 unit tests covering nested-subquery and string-literal cases.
- **Regression Risk:** LOW — also currently latent (emitted SQL has no subquery tail clauses; proximity `EXISTS` subqueries are bare), but the helper feeds `SQL`, `COUNT_SQL`, and `BREAKDOWN_SQL`.
- **Follow-Up:** NONE

### Disabled logging still did string/serialization work (Low review finding)

- **Symptom:** With a no-op logger, every query still built `'...' + buildResult`, `JSON.stringify(rows[0])`, `Object.keys(...)`, three `.substring()`s, a `.split('\t')` — JS evaluates call args eagerly.
- **Root Cause:** No gate around expensive log payloads.
- **Fix:** `ctx.debug` flag; `log` is a no-op unless debug is on, and the six expensive payloads are wrapped in `if (debug)`. Worker added `DEBUG = false`; harness wires it to `-v`. Doubles as the long-flagged "gate console.log" cleanup for the pipeline path.
- **Regression Risk:** NONE — default-off run shows 0 `[pipeline]` lines; `-v` shows 70.
- **Follow-Up:** NONE

### Failed project loads could leave queries running against a half-loaded DB (Medium review finding)

- **Symptom:** `loadDbFromBytes` swapped `activeDb` before `computeSummary` validated it; a `computeSummary` throw left `activeDb` on the failed replacement, and the catch's `ready = !!activeDb` re-enabled queries against it.
- **Root Cause:** DB swap happened before validation.
- **Fix:** `loadDbFromBytes` → `deserializeDb` (returns a DB, never touches `activeDb`). `loadProject` now builds + validates (`computeSummary` on the new DB) *before* committing the swap; on any failure it closes the half-built DB and leaves the last-good `activeDb` intact. Also fixes the teardown-ordering sharp edge prior summaries flagged.
- **Regression Risk:** LOW (worker-only; pure JS, parses clean)
- **Follow-Up:** Browser verification (point a manifest entry at a bad `dbUrl`, switch, confirm shell still queries the previous project).

### Streamed DB download assumed `Response.body` present (Low review finding)

- **Symptom:** `getDbBytes` did `resp.body.getReader()` unconditionally; `resp.body` can be null even on a 200 in some environments.
- **Root Cause:** No fallback for body-less responses.
- **Fix:** Guard on `resp.body && getReader`; else `new Uint8Array(await resp.arrayBuffer())` with a single completion `progress` tick. Both paths converge on the same `bytes`, preserving the cache-put.
- **Regression Risk:** NONE (localized guard, parses clean)
- **Follow-Up:** NONE

## Notes / Design Decisions

- **Shared-core over standalone replica (user-selected):** the harness imports the real `runQuery`, so it can't drift from the browser path. This was the whole point — a replica could pass while production broke.
- **sqlite-wasm over `node:sqlite`/better-sqlite3 (user-selected):** same SQLite build the browser ships, deserialized the same way — true engine parity.
- **`VACUUM INTO` for snapshots:** reads live (WAL-inclusive) state, writes a self-contained rollback-journal DB, and compacts. No source mutation, no `-wal` dependency.
- **One `<project>` identifier drives everything:** source folder, `sourceBase`, and snapshot name — index-in-place is what makes recorded paths resolve against `sourceBase`.
- **`debug` gate is the real fix for log overhead,** not a no-op logger — JS evaluates arguments eagerly, so payloads must be skipped with `if (debug)`.

## Freeform Thoughts

The harness paid for itself on its first real run: the WAL-mode snapshot would have shipped a broken browser app, and `make web-test` turned a silent production failure into a one-line diagnosis. That's the strongest possible argument for the shared-core decision — the test exercises the real path, so a real bug surfaced instead of a replica passing.

The recurring theme in the review fixes is "latent but structurally wrong": `limit<=0`, `injectWhereClause`, the failed-swap readiness — none are reachable today, each guarded by something upstream (the C parser, the emitted SQL shape). Fixing them is cheap insurance, but it's worth noting how much of the bridge's correctness currently rests on invariants enforced elsewhere rather than locally. The validate-before-swap fix is the one that actually hardens a real failure mode (bad/corrupt snapshot) rather than a hypothetical one.

The `html/sources/` convention finally gives the multi-DB dropdown a real home, and the index-in-place insight (the user's) is the keystone — without it, `sourceBase` routing and recorded paths drift. Worth foregrounding in the docs because it's the non-obvious step.
