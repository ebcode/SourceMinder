# xterm.js Reference Guide for a Worker-Backed qi Terminal

## What xterm.js should own

For your scenario, xterm.js is best treated as the terminal surface, not as the shell. Its job is to render terminal output, maintain scrollback, expose focus and selection behavior, parse terminal control sequences, and accept keyboard/paste input in a terminal-compatible way. Your shell-like prompt semantics — current input buffer, cursor index inside that buffer, history navigation, and Enter-to-submit behavior — should live in a small JavaScript line editor that you control. That split lines up with xterm.js’s API shape: `onData` is about terminal input bytes/strings that would normally go to a PTY, `onKey` tells you what string would be sent, and `attachCustomKeyEventHandler` exists specifically to let integrations decide which keys xterm.js should process and which it should not. citeturn8search8turn26view1turn27view1turn26view0

That split is especially sensible in your case because SourceMinder is already a substantial C codebase. The repository describes SourceMinder as a multi-language code indexer built on SQLite and tree-sitter, and the current `query-index.c` file is listed at 3,598 lines and 146 KB. Keeping prompt editing in JS lets the browser-facing UX stay small and deterministic while the ported C/WASM side stays focused on query execution and text generation. citeturn18search0turn19view0

## Why arrow keys behave like escape sequences

What you are seeing with arrow keys is normal terminal behavior, not a bug in xterm.js. Classic terminals have “normal” and “application” modes for special keys. In normal mode, cursor keys send CSI-style sequences that begin with `ESC [`; in application mode, they send SS3-style sequences that begin with `ESC O`. The xterm manual describes this explicitly, and xterm.js exposes the corresponding terminal mode state through `term.modes.applicationCursorKeysMode`. citeturn33search0turn35view0

xterm.js also documents that `onData` fires with whatever string results from typing or pasting, and `onKey` exposes the string that will be sent in the data event. So when Up/Down/Left/Right show up as fragments like `[A`, `[B`, `[D`, `[C`, what is really happening is that your integration is letting xterm generate terminal key sequences, then your app is treating those sequences as ordinary prompt text instead of intercepting them as editor commands. The missing visible `ESC` is usually an artifact of how the string is logged, displayed, or stripped in your own pipeline; the important point is that you are seeing terminal control input rather than shell editing. citeturn26view1turn27view1turn33search0turn33search1

For a JS-owned prompt buffer, the right approach is to intercept ArrowUp, ArrowDown, ArrowLeft, and ArrowRight before xterm processes them, using `attachCustomKeyEventHandler`, and return `false` for the keys your line editor handles itself. That prevents xterm from emitting terminal cursor-key sequences for those keys and gives your editor full control over history traversal and cursor movement inside the prompt buffer. If you ever need to inspect xterm’s current terminal mode for debugging, `term.modes.applicationCursorKeysMode` and `term.modes.bracketedPasteMode` are the relevant reads. citeturn26view0turn35view0turn24search3

## xterm.js reference for a JS-owned prompt

The first practical detail is bootstrapping. The official import guide says the preferred path is ES modules and warns that you must include the xterm CSS stylesheet. The `Terminal.open()` docs also matter more than they look: the parent element must already be visible and have dimensions when you call `open()`, because xterm performs DOM-based measurements at that moment. If you want the terminal to follow container size automatically, the official addon list includes `@xterm/addon-fit`, whose purpose is to fit the terminal dimensions to a containing element. citeturn25view0turn26view3turn16view0turn7search20

The key Terminal surfaces for your prompt layer are these. `focus()` and `textarea` control how the terminal receives input. `onKey` and `onData` let you observe what xterm would send to a backend. `attachCustomKeyEventHandler()` lets you block xterm’s default handling for editor keys. `input()` lets you inject synthetic terminal input through the same application-side path as if the user had typed it. `cols`, `rows`, and `onResize` are what you use when your prompt renderer needs to know the current viewport width, especially if you ever support wrapped input. citeturn26view4turn4view2turn26view1turn26view0turn26view2turn38view0

The most reliable rendering strategy for a shell-like prompt is to treat xterm as a VT terminal and redraw the current input line with terminal control sequences, not by poking at DOM nodes and not by treating xterm’s buffer as the source of truth. xterm.js supports the exact primitives you want for this: carriage return moves to the start of the row, erase-in-line clears the active row, cursor-forward and cursor-backward move left or right, and horizontal-absolute places the cursor at a specific column. In practice, that means your line editor can keep a pure JS state object such as prompt text, editable buffer text, cursor index, history list, and history cursor, and then redraw from that state using standard VT movement/erase behavior. citeturn14view0turn43view0turn13view1turn13view5

The crucial design choice is this: xterm’s buffer is display state, not your canonical prompt model. xterm does expose rich buffer access — `buffer.active.cursorX`, `buffer.active.cursorY`, `getLine()`, and line-to-string translation through `IBufferLine.translateToString()` — but that is best used for debugging, copy features, or advanced diagnostics, not as the primary model of the editable command line. The docs explicitly note that buffer reads and line/cell objects should be used immediately and carefully because terminal updates can make them stale. citeturn11view0turn40view0

One rough edge that matters a lot for prompt re-rendering is that `write()` and `writeln()` are asynchronous. xterm.js states that the change is not reflected in the buffer immediately and that you should use the callback, or `onWriteParsed`, if you need to know when parsing has completed. For a JS-owned prompt, that means worker output should go through a small write queue, and prompt redraw should happen only after the preceding output chunk has actually been parsed. Otherwise, async qi output can race your prompt repaint and leave the cursor or the visible line in the wrong place. citeturn4view7turn27view0

Two options are unusually relevant to your use case. `convertEol` exists specifically for non-PTY sources and makes `\n` behave like `\r\n`, which is often what you want when plain text from workers or APIs is not coming from a real terminal backend. And `disableStdin` can hard-disable input if you decide there are moments when the prompt should be completely frozen, though in many integrations a JS-side `executing` flag is enough. citeturn29view0

## xterm.js reference for output, paste, copy, and scrollback

For output, the simplest discipline is append-only terminal history plus a separately owned live prompt line. `write()` accepts either strings or `Uint8Array`; strings are treated as UTF-16 and raw bytes as UTF-8. That gives you flexibility: Emscripten `print`/`printErr` usually hand you strings, but if some future path streams UTF-8 bytes directly, xterm can still consume them. `writeln()` just adds a line break after the supplied data. citeturn4view7turn34search1

For paste, the Terminal API gives you two useful building blocks. `paste()` writes text to the terminal while performing the transformations xterm considers necessary for pasted text, and `onData` explicitly says it fires for typing or pasting. xterm.js also tracks bracketed paste mode in `term.modes.bracketedPasteMode`, and `ITerminalOptions.ignoreBracketedPasteMode` lets you force pastes to omit the `ESC [ 200~` and `ESC [ 201~` wrappers even if the shell side enabled bracketed paste. In your narrowly scoped browser shell, where prompt editing is yours and you are not trying to emulate a full remote PTY, treating paste as direct JS buffer insertion or using `paste()` with bracketed-paste complexity intentionally simplified is usually the cleanest choice. citeturn26view3turn26view1turn35view0turn28view1

For copy and selection, xterm already gives you most of what you need. `getSelection()` exists specifically to support copy behavior outside xterm.js, `hasSelection()` and `getSelectionPosition()` tell you whether a selection exists, `onSelectionChange` lets your UI react to it, and `select`, `selectAll`, `selectLines`, and `clearSelection` provide explicit programmatic controls. The official addon list also includes `@xterm/addon-clipboard`, but for a minimal shell-like terminal, the core selection APIs plus your browser copy path are usually enough. citeturn26view4turn26view2turn27view0turn4view4turn24search1

If qi output can be long, scrollback matters. `scrollback` defaults to 1000 rows, `scrollOnUserInput` defaults to true, and `scrollToBottom()` is available if you want to explicitly re-stick the viewport after command execution. For a search/query tool, increasing scrollback above the default is usually worth it so that the user can review prior results without losing the terminal feel. citeturn28view3turn4view6

The two advanced xterm objects that are actually relevant to your case are `IMarker` and `IDecoration`, but they are optional, not foundational. A marker tracks a specific line even as scrollback is trimmed and lines are inserted or removed, which makes it useful for remembering where a command started or where a current prompt line used to be. Decorations are associated with markers and DOM elements and can color or annotate portions of the terminal, but xterm marks them experimental, and `allowProposedApi` is false by default. For your intentionally minimal terminal, markers are the more realistic advanced tool; decorations are something to defer unless you later want status badges or non-text affordances. citeturn26view6turn10view2turn26view7turn10view0turn10view1turn28view0

One security point is worth keeping even in a plain-text design. xterm’s security guide warns that terminal data should be treated as untrusted when it crosses into DOM-level features, especially through buffer access, title handling, linkification, or parser hooks. If you keep qi output as plain text, avoid `innerHTML`, and do not add clickable DOM enrichments around terminal data, you stay in the safest part of the design space. citeturn23view0

## Worker and WASM reference for qi and sqlite

Running qi and SQLite in workers is the right default for browser responsiveness. Emscripten’s runtime docs explain that the browser event model is cooperative and a blocking loop on the main browser thread makes the page hang. They also note that synchronous file-style access is problematic because JavaScript only supports asynchronous file access outside web workers; Emscripten’s answer is a virtual filesystem, usually MEMFS, backed by asynchronous loading before code runs. citeturn30view0turn30view1

For qi.wasm specifically, the Emscripten `Module` object is the central reference page to keep open. `Module.print` and `Module.printErr` are the stdout/stderr hooks. `Module.onRuntimeInitialized` tells you when compiled code is safe to run. `Module.locateFile` decides where the `.wasm` and related assets are loaded from. `Module.preRun` is the supported place to create directories or files before `main()` starts. `Module.arguments` provides `argc/argv` values. And the compiler setting `INVOKE_RUN` exists precisely so you can disable automatic `main()` execution and call `main()` yourself later with `Module.callMain()` if you keep a command-style entrypoint. If instead you export C functions and treat qi more like a library, Emscripten’s JS interop docs point you to `ccall`, `cwrap`, or direct exported calls. citeturn32view0turn42view0turn30view3

For SQLite, the official WASM docs matter because they constrain your architecture more than many people expect. SQLite states that only the JS thread that loads `sqlite3.js` can use that API directly, that each thread gets its own independent WASM runtime with no shared state, and that each runtime has its own virtual filesystem. The worker-oriented APIs are therefore not just a convenience layer; they are the right way to structure browser-side SQLite access when you want the database off the UI thread. The official Worker1/Promiser docs say the Promiser runs SQLite in its own dedicated worker and that each Promiser instance loads its own distinct copy of SQLite with its own WASM sandbox. The immediate consequence is that separate qi and SQLite workers cannot share a database handle or in-memory SQLite state directly; their boundary must be messages, result rows, SQL requests, or plain text, not shared handles. citeturn21view2turn21view1turn36view0

There is also a deployment footnote. SQLite’s own CSP page says environments loading SQLite WASM may need a CSP that allows WASM compilation, specifically `script-src 'wasm-unsafe-eval'`, if you emit CSP at all. If your qi.wasm and sqlite.wasm are both browser-loaded assets, check this early rather than after the rest of the pipeline is working. citeturn21view3

## Recommended architecture

The strongest recommendation is a three-layer split. Keep xterm.js and the line editor on the main thread. Keep qi execution and orchestration in a worker. Keep SQLite in its official worker/promiser worker. The main thread owns prompt state, history, cursor movement, copy/paste behavior, and terminal redraw. The orchestration worker owns command execution state and talks to either qi.wasm, the SQLite worker, or your read-only API. The SQLite worker owns the browser-side database. That separation matches xterm’s terminal-centric input model, SQLite WASM’s thread isolation model, and the browser’s responsiveness constraints. citeturn26view0turn26view1turn21view2turn36view0turn30view0

The command lifecycle should be equally strict. On Enter, commit the current JS prompt buffer, echo the submitted command into terminal history, clear the live editor state, and send a single command request to the worker layer. While output is streaming back, append it with `term.write()` through a queue. After the last chunk has actually parsed, redraw the next prompt from JS state. That exact sequencing is what avoids the classic “worker output lands inside my editable prompt” problem, and it is directly motivated by xterm’s asynchronous `write()` semantics. citeturn4view7turn27view0

For the qi side, keep the browser-facing contract plain-text and command-oriented, but do not force shell editing into WASM. If you preserve a program-like qi entrypoint, Emscripten’s `Module.arguments`, `print`, `printErr`, `preRun`, `onRuntimeInitialized`, and optional manual `callMain()` are the right hooks. If you instead refactor the emerging qi port into exported callable functions, using `ccall`/`cwrap` or direct exports gives you a cleaner long-running worker model. Either way, xterm should never be your command parser and qi.wasm should never be your line editor. citeturn32view0turn42view0turn30view3turn26view0turn26view1

Given your read-only, API-only persistence model, browser storage should not be the authoritative source for file-dependent flags. Let the browser own the in-browser SQLite DB for DB-backed queries, let the API own file-backed reads, and let the terminal stay a rendering surface for plain text coming back from those two backends. That keeps responsibilities crisp and avoids overloading Emscripten’s virtual FS with persistence semantics you explicitly do not want. citeturn21view2turn30view1

## Three architecture directions

The first direction is the one I would default to: a JS-first shell surface. In this model, xterm renders, the JS line editor owns prompt semantics, the SQLite worker answers DB-backed requests, and qi.wasm is either thin or optional. This path best matches xterm’s API, minimizes terminal weirdness, and lets you evolve the port incrementally without coupling shell UX to the C port. citeturn26view0turn26view1turn21view2

The second direction is a C-fidelity runner worker. In this model, qi keeps a CLI-shaped WASM entrypoint, and the worker emulates enough process-like environment to invoke it repeatedly using `Module.arguments`, stdout/stderr hooks, `preRun`, runtime initialization, and either manual `callMain()` or exported functions. This is the best choice if your priority is preserving more of `query-index.c`’s current behavior and output formatting while still keeping prompt and history in JS. citeturn32view0turn42view0turn30view3

The third direction is a heavier native-style port using Emscripten threading features. Pthreads are the more portable option for larger C/C++ ports, but Emscripten documents that browser pthreads require `SharedArrayBuffer` and therefore correct COOP/COEP headers, and it recommends getting `main()` off the UI thread with `PROXY_TO_PTHREAD` to avoid blocking-path hazards. Wasm Workers can be smaller and more web-native for WASM-only code, but Emscripten documents that they always start asynchronously and do not have pthread conveniences like built-in JS proxying. I would treat this direction as a last resort if the port pressure from POSIX-style code is high enough that the extra deployment and threading complexity is justified. citeturn30view4turn37view0

## Open questions and limitations

The main unresolved design choice is whether your prompt will stay single-line or eventually support fully wrapped multi-line editing. xterm exposes `cols`, resize events, and the standard VT cursor/erase sequences you would need, but wrapped-input editing introduces enough display-state complexity that it deserves a deliberate algorithm of its own; this report only recommends the approach, not a single canonical wrapping implementation. citeturn38view0turn43view0turn13view1

A second implementation decision is whether repeated qi invocations will reuse one long-lived Emscripten runtime or run in a fresh-per-command worker/process style. Emscripten clearly supports both the “manual main invocation” model and the “export callable functions” model, but the better choice depends on how much global/static state survives from one qi run to the next in the code you keep from `query-index.c`. citeturn42view0turn32view0turn30view3
