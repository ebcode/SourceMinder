## Work Completed

### Round 1

- **Finding 1 — project-switch / in-flight-query race (FIXED):** Added a promise-chain mutex (`opQueue` + `enqueue()`) in `qi-worker.js` so `init`/`load-project`/`query` run strictly one-at-a-time. A `load-project` can no longer run `loadDbFromBytes()` (which closes/replaces the global `activeDb`) while a query is mid-flight. Moved the `!ready` query check inside the queued turn and dropped the now-unneeded `async` on `onmessage`. Added a `switching` flag in `app.js` so an in-flight query's `output`/`error` writes its text but does not re-enable terminal input while a switch is still loading (the `ready` handler clears it).
- **Finding 2 — negative-cache poisoning (FIXED):** `SourceCache.fetchOne()` now caches `null` only for definite misses (HTTP 404/410). Transient failures (5xx, 429, network errors) are left uncached, so `fetchMissing()` retries them on the next source query instead of permanently returning "could not read file" for the rest of the session.
- **Finding 3 — source-payload memory overhead (FIXED):** Collapsed the source-blob handoff from 4 full-size copies to 2. Changed the wire format from length-prefixed (`path\n<len>\n<bytes>`) to NUL-framed (`path\0content\0`) written straight into the WASM heap. New `marshalSources()` in `qi-worker.js` `_malloc`s one heap buffer and writes records with `stringToUTF8` (encodes directly into the heap); `runQuery` passes `(ptr, len)` as numbers and `_free`s in a `finally`. `source_map_parse()` now walks the buffer storing pointers into it (zero per-file `malloc`/`memcpy`); `source_map_free()` frees only the index array. Content stays NUL-terminated in place, so the render twin is untouched.

### Round 2

- **Finding 4 — failed-switch UI deadlock (FIXED):** The round-1 `switching` guard made the `error` handler a no-op during a switch, but a failed `load-project` only ever produces an `error` (never `ready`) — so `switching`/`isExecuting`/`disabled` stuck forever and froze the shell until reload. Tagged every worker error post with a `phase` (`'init'`/`'load'`/`'query'`). Main thread now recovers on `load`/`init` errors (clears flags, re-enables the dropdown, reverts the select to `currentProjectId`); a `query` error while a switch is queued still stays gated. Worker side: on a `load-project` failure, `ready = !!activeDb` restores readiness so queries against a still-loaded prior DB are not permanently blocked by the eager `ready = false`.
- **Finding 5 — `--within` totals/breakdown unscoped (FIXED):** The worker injected the within `AND (...)` clause into `sql` only; `COUNT_SQL`/`BREAKDOWN_SQL` are precomputed in `qi_web_build()` from the base SQL before WITHIN post-processing, so "Found N matches" and "Result breakdown:" reflected the unscoped query. Added `injectWhereClause()` (inserts ahead of the earliest trailing `GROUP BY`/`ORDER BY`/`LIMIT`, else appends) and hoisted `withinWhere` to `runQuery` scope; the main SQL, count, and breakdown now all run through it. No-op when `--within` is absent (`withinWhere === ''`).
- **Finding 6 — invisible startup failures (FIXED):** The terminal installs only after the first successful `ready`, so `init()`/first-`loadProject()` failures arriving via `case "error"` hit a `termWrite` no-op and never called `showError()` — the page hung on its status line. The `error` handler now routes pre-install failures (`!terminalInstalled`) to the visible `showError()` banner; post-install errors still write to the terminal. Combined with Finding 4's recovery, a first-project failure also re-enables the (already populated) dropdown so the user can pick another project.

## Issues Encountered

### Source blob routed through the `ccall` stack

- **Symptom:** Not a runtime failure observed this session, but identified while fixing Finding 3.
- **Root Cause:** Passing the source blob as `ccall(..., 'string', ...)` marshals the entire payload via `stackAlloc` onto the WASM stack — a latent stack-overflow risk for multi-file context queries, on top of the redundant copies.
- **Fix:** Source payload now transfers via an explicit `_malloc`'d heap buffer + pointer/length, off the stack entirely. Only the small, LIMIT-bounded `build_info`/`rows_tsv` still use `ccall 'string'`.
- **Regression Risk:** MEDIUM — wire-format + ABI change; needs a real `make web` build and a browser test of `-e`/`-C`/`-A`/`-B`.
- **Follow-Up:** User to rebuild and verify source expansion still renders.

### `switching` guard introduced a failed-switch deadlock (round-1 regression caught in round 2)

- **Symptom:** Finding 4 — a failed project switch (bad `dbUrl`, manifest error) leaves `switching`/`isExecuting`/`projectSelectEl.disabled` stuck `true` forever; the shell is unusable until reload.
- **Root Cause:** The round-1 `switching` flag made `case "error"` a deliberate no-op during a switch, but only `case "ready"` clears those flags — and a failed `load-project` never reaches `ready`. The worker also left `ready = false` (set eagerly by `loadProject`), blocking all later queries.
- **Fix:** `phase`-tagged worker errors; main-thread recovery on `load`/`init`; worker restores `ready = !!activeDb`.
- **Regression Risk:** LOW — pure JS, syntax-checked; the recovery path mirrors the `ready` path.
- **Follow-Up:** Consider collapsing `switching` + `isExecuting` into a single explicit state enum so a new gate can't silently create another stuck state.

### `strcasecmp` implicit-declaration warning during syntax check

- **Symptom:** `gcc -fsyntax-only` on `qi-web-entry.c` (with a stubbed `emscripten.h`) warned `implicit declaration of 'strcasecmp'` at line 389.
- **Root Cause:** Pre-existing; the standalone syntax check lacks the `web` target's header/flag environment that declares `strcasecmp`. Not introduced by this session's changes.
- **Fix:** None applied — out of scope for these findings and not present in the real emcc build. Noted for awareness.
- **Regression Risk:** NONE (pre-existing, not triggered by these edits)
- **Follow-Up:** Could mirror the `query-index-web.c` fix (`#include <strings.h>`) into `qi-web-entry.c` if it ever surfaces in the real build.

## Residual Risks / Not Verified

- **No real build yet.** All three fixes are syntax-checked only. Finding 3 changes the `qi_web_format` ABI and the source wire format — a typo would only surface at `make web` or in the browser.
- **`_malloc`/`_free`/`stringToUTF8`/`lengthBytesUTF8` availability.** Confirmed in `configure`'s `EXPORTED_FUNCTIONS`/`EXPORTED_RUNTIME_METHODS`, but `marshalSources()` has not been exercised against the real module.
- **NUL-framing drops embedded-NUL support.** Content with a literal `\0` would be truncated. This matches the prior `ccall 'string'` constraint (the render twin already treats content as a C string), so it is not a regression — but it is now an explicit format assumption.
- **Finding 2 retry path is untested in practice.** The logic is simple (don't cache non-404/410), but no flaky endpoint was available to confirm end-to-end recovery.
- **Finding 4/5/6 are syntax-checked only.** No browser run yet. Finding 5 in particular assumes `--within` queries always carry a base `WHERE` (so the appended `AND (...)` is well-formed) — the same assumption the pre-existing main-SQL injection made, and the reviewer confirmed rows scope correctly, but it is not separately validated. Finding 4's `ready = !!activeDb` recovery is only correct because `getDbBytes()` fails *before* `loadDbFromBytes()` tears down the old DB; a failure *inside* `loadDbFromBytes` (after it nulls `activeDb`) correctly yields `ready = false` but loses the prior project — a pre-existing teardown-ordering sharp edge, not addressed.
- **Pre-existing returned-string leak (out of scope).** `ccall` with return type `'string'` does not free the C-side `wo_steal`'d buffer; `_qi_web_free_result` is exported but the worker does not call it. Noted, not addressed.

## Notes / Design Decisions

- **Mutex over generation-token (user-selected):** A promise-chain mutex prevents *both* interleavings and lets the in-flight query complete against its correct DB before the switch tears it down — so its output is valid, never stale, and need not be discarded. The token approach would have proceeded immediately but wasted the in-flight query's work and required a re-check after every `await`/before every `activeDb` use. Trade-off accepted: a switch requested mid-source-fetch waits for that network fetch.
- **`switching` flag is main-thread polish, not the core fix.** The worker mutex alone closes the data race; `switching` only keeps the terminal UI from re-enabling input during the window between an in-flight query finishing and the queued switch completing.
- **Negative caching limited to 404/410:** These are the only "definitely absent" signals for a static file origin. Everything else is treated as recoverable.
- **`getFiles()` returns records, not a heap buffer:** Keeps `SourceCache` backend-agnostic (the "swap `fetchOne` for a batch API" seam from QI_WEB_FILE_PLAN.md survives). Heap marshaling lives in `marshalSources()`, which is the only piece that knows about `qiModule`.
- **NUL-framing chosen over keeping length-prefix + heap transfer:** Length-prefix would have required either per-file copies (to NUL-terminate) or making content length-aware throughout the render twin. NUL-framing terminates content in place for free, so the twin is untouched.

## Freeform Thoughts

All three findings were legitimate and pointed at the same underlying theme: the bridge was treating the worker as if it were synchronous. The race existed only because `runQuery` has exactly one `await`; the memory overhead existed because the easy path (`ccall 'string'`) hides a stack copy. Fixing them surfaced two adjacent issues worth tracking — the returned-string leak and the `console.log` density — neither urgent, both the kind of thing that compounds.

The mutex was the satisfying fix: one small primitive (`enqueue`) that closes the race in both directions and made the `!ready` check correct almost incidentally. The `switching` flag felt slightly grafted-on by comparison, but the alternative (letting the terminal re-enable mid-switch) is a real UX papercut. Worth keeping an eye on whether `switching` and `isExecuting` should eventually collapse into a single state enum.

The thing I most want before the next C-side change is the headless export harness — every bridge change this session ended in "please run make web," and that round-trip is the main drag on iteration speed here.

The "bridge UI state machine" is the proposed idea of replacing the two ad-hoc boolean flags (isExecuting and switching) in app.js with one explicit state variable (e.g. idle/querying/switching/failed) so that every transition has exactly one defined clearing path — making stuck states like the round-2 deadlock structurally impossible rather than relying on remembering to reset each flag in each handler.
