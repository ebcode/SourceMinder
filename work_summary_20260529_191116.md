## Issues Encountered

### CLI/web TOC parity: web caps TOC output at 25 rows, CLI does not

- **Symptom:** `qi % -f negroni.go --toc` showed `[Limit reached: 25 shown, 26 total]` in the browser (dropping `voidMiddleware`), while the native CLI showed all rows.
- **Root Cause:** The native CLI defaults `int limit = 0` (unlimited) at `query-index.c:2724`; `--toc` early-exits using that 0, so TOC is never capped (there is no literal `25` in `query-index.c`). The web `parse_command` defaulted `cmd.limit = 25` for *all* modes, so TOC inherited the cap and emitted `LIMIT|25`; `format_toc_web` then printed `[Limit reached...]` whenever `total_available > total_shown`.
- **Fix:** Changed the web default to `0` (unlimited) to match native — `qi-web-entry.c:230` (the real parse-time init) `cmd.limit = 25 → 0`, the cleanup-reset twin at `:180` likewise, and the JS fallback `html/qi-pipeline.js:145` `buildLines.LIMIT || '25' → || '0'`. The pipeline already treats `limit <= 0` as "no limit" in every mode, and the `--limit` flag's own validation still rejects explicit `<= 0`.
- **Regression Risk:** LOW — this changes the **default** for *all* web modes (regular search is now unlimited by default, matching the CLI), not just TOC. Worth an eye on whether any UX intentionally relied on the 25-row search cap (user explicitly confirmed it should be "yanked out entirely").
- **Follow-Up:** Needs `make web` + hard reload. **First rebuild attempt still emitted `LIMIT|25`** because the initial edit only touched the cleanup-reset function (`:180`), not the parse-time init (`:230`); that was corrected. A second rebuild is required to confirm `LIMIT|0`.

### First `make web` rebuild appeared not to take

- **Symptom:** After the user ran `make web` and hard-reloaded, `[Limit reached: 25 ...]` persisted.
- **Root Cause:** Two `cmd.limit = 25` sites exist; the first edit changed `free_command`'s reset (`:180`), not `parse_command`'s init (`:230`). Inspected the freshly-built WASM via a throwaway harness loader (`tmp/check_toc_limit.mjs`) and saw it still emit `LIMIT|25`, which localized the miss.
- **Root Cause confirmation tool:** `tmp/check_toc_limit.mjs` calls `loadQiModule('./html')` then `ccall('qi_web_build', ...)` and greps the build_info for `LIMIT|` — direct proof of what the binary emits, no browser needed.
- **Fix:** Edited `:230` as well; `grep` confirms no `= 25` / `'25'` defaults remain in the web bridge.
- **Regression Risk:** NONE
- **Follow-Up:** Confirm `LIMIT|0` after the next rebuild (re-run `tmp/check_toc_limit.mjs`).

## Notes / Design Decisions

- **`<optgroup>` over literal `<hr>`:** inside a `<select>` the only standards-compliant grouping primitive is `<optgroup>`; it both separates *and* labels each language group. Offered the disabled-separator-option alternative if unlabeled rules are ever wanted.
- **`term.scrollPages()` over synthesizing a Shift+PageUp keystroke:** calling xterm's own scroll method is exactly what it does internally for Shift+PageUp/Down — same effect without the fragility of re-dispatching a fake `KeyboardEvent`.
- **Limit default = 0 means "unlimited" by convention** throughout the pipeline (TOC/files/search all guard with `limit > 0`), so making the *default* 0 is the single-point fix for CLI parity rather than special-casing TOC.
- **negroni placed first** because only `projects[0]` auto-downloads; the default project just needs to be the smallest *placed at the top*, not the smallest overall.

## Tooling Ideas

## Freeform Thoughts

The whole TOC bug was a one-line default that diverged silently between the native `main()` (`limit = 0`) and the web `parse_command` (`limit = 25`) — exactly the class of drift the parity-by-twinning design is supposed to prevent, and exactly the class it *can't* catch automatically because defaults aren't twinned functions, just twinned constants. The harness exercises the pipeline but asserts on presence of substrings, not on CLI-equivalence, so a 25-vs-unlimited difference sails through green. A genuine native-vs-web differ (Tooling Idea 2) is the thing that would turn this category of bug from "user notices in the browser" into "CI fails."

The other lesson is mechanical: I edited `:180` first and reported it fixed, but `:180` was the cleanup-reset, not the parse-time init at `:230`. Two identical `cmd.limit = 25` lines, and grep-by-value would have shown both immediately — I reached for it only after the rebuild came back wrong. When a default is "the same line in two functions," grep the value, not the function.
