## Issues Encountered

### `ESCAPE Backslash Doubling in X-Macro`

- **Symptom:** `qi % -p wo` in browser produced `SQLITE_ERROR: ESCAPE expression must be a single character`.
- **Root Cause:** `query-index-web.c X-macro blocks (lines 411, 423) used ESCAPE '\\\\' (4 backslashes in C source → 2 backslashes in the SQL string). SQLite parses '\\' as a two-character string, violating the single-character ESCAPE requirement. The native CLI (query-index.c line 970) correctly uses ESCAPE '\\' (2 backslashes in C → 1 in SQL). The web extraction had an extra layer of backslash escaping, likely introduced when the author thought vsnprintf format strings interpret backslashes (they don't — only % sequences are special).`
- **Fix:** `Changed ESCAPE '\\\\' → ESCAPE '\\' at query-index-web.c:411 and :423, matching the native CLI.`
- **Regression Risk:** `LOW`
- **Follow-Up:** `NONE`

### `scope/namespace Missing from QueryFilters in Web Build`

- **Symptom:** `make web failed with "no member named 'scope' in 'QueryFilters'" and "no member named 'namespace' in 'QueryFilters'".`
- **Root Cause:** `scope and namespace columns in shared/column_schema.def are gated by #if ENABLED(TYPESCRIPT) || ENABLED(PHP) || ..., and no ENABLE_* macros were defined for the web build.`
- **Fix:** `Added -DENABLE_TYPESCRIPT=1 to the web and web-smoke emcc flags in the configure script.`
- **Regression Risk:** `LOW`
- **Follow-Up:** `NONE`

- `Debug fprintf calls inside query-index-web.c (WITHIN RANGES, Within lookup SQL, anchor query SQL) still go to stderr which is invisible in the browser. Only the main query SQL is surfaced in the terminal output.`

## Notes / Design Decisions

- `Chose a web column registry (WebColSpec table with name, header, header_compact, tsv_index, width, is_int) over porting the CLI's function-pointer-based ColumnGetter approach. The TSV-index-based model is simpler and avoids needing a RowData struct in the web format function.`
- `Used parse_col_flag_values() helper with the pattern "always set show=1, then collect following non-flag tokens as filter values" — matches the CLI's X-macro generated behavior exactly.`
- `The SHOW_IF macro for COLUMNS| line construction checks both cmd.verbose (verbose mode shows all) and each flag's .show (flag-specific toggle). --columns overrides everything when present.`
- `Chose attachCustomKeyEventHandler over parsing escape sequences in onData for arrow key handling — the report recommends it, and it avoids fragile CSI/SS3 sequence parsing and application/normal cursor key mode tracking.`
- `Prompt redraw uses raw VT sequences (\r\x1b[K clear-line, \x1b[NC cursor-forward) called via term.write() directly — avoids the termWrite() \n→\r\n wrapper since these don't contain newlines.`

## Freeform Thoughts

`The ESCAPE backslash bug was a second encounter with the same class of error (the first being the vsnprintf measurement-mode bug in the previous session). Both were C string escaping issues at the boundary between the custom mprintf shim and vsnprintf. A pattern is emerging: whenever a format string literal contains backslashes intended for SQL, the developer must count C-source escapes (how many \ characters in the .c file), C-string-escapes (how many \ in memory), vsnprintf pass-through (how many \ in the output), and SQL parsing (how many \ SQLite sees). Four layers for one character. The QUERY-INDEX-WEB-DEVELOPMENT-GUIDE.md documents this now, but a linter that checks for ESCAPE '\\\\' in web extraction files would be even better.`

`The column flag implementation was satisfying because it leveraged three existing pieces that were already in place: the QueryFilters struct (X-macro), the build_common_filters_web function (X-macro), and the web column registry (format function). The only new code was the flag parser and the POPULATE_COL_FILTER bridge between them. That's a good sign that the extraction architecture is stabilizing — new features slot into existing seams rather than requiring new infrastructure.`

`The arrow key rewrite touched the largest surface area of any app.js change since the xterm.js migration. The VT-based redraw approach feels fragile (raw escape sequences written directly to term.write()) but is actually what xterm.js recommends for prompt-line editing. The next risk point is when output from the worker contains ANSI escape sequences (e.g., if qi ever outputs color) — those would need to be distinguished from the prompt redraw sequences.`

`There's a growing gap between what the web bridge supports and what the CLI supports. The remaining flags (--and, --within, --files, --toc, -e, -C/-A/-B) are individually not huge, but collectively they'd roughly double the web bridge complexity. The report's Architecture Direction 3 (WASIX/pthreads) becomes more attractive the more flags we implement manually.`
